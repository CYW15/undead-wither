# 设计决策记录（ADR）

> 凋亡回响 · Minecraft 1.20.1 高难度凋灵主题整合包 · 共 13 条

本文档记录本项目在设计阶段做出的关键决策，格式为「问题 → 决策 → 理由 → 代价 → 落点」。来源是 task/需求确认清单.docx：共 106 个问题，其中 37 项标为 ★ 决策点（会改变实现结果的岔路），本人对其中的关键项逐条拍板，其余采用经核对的默认值——这是项目负责人应有的介入密度，而不是替执行方决定每一处实现细节。


## ADR-01　交付形态选 mrpack，而非“版本文件夹”

- **问题**｜Q1★　最终交付物做成什么形态？（默认：PCL/HMCL 可直接导入的版本文件夹）
- **决策**｜采用 Modrinth 的 .mrpack 格式作为主交付物，同时另出专用服务端包与起始存档。
- **理由**｜单一文件即可分发，内含 modrinth.index.json 与每个模组的 sha1/sha512，对方导入时能校验完整性——版本文件夹做不到这一点，玩家自己删错一个 jar 都查不出来。
- **代价**｜需要维护索引文件与哈希；查不到哈希的模组（CurseForge 独占、自制改版）只能塞进 overrides/mods，包体因此偏大（309 MB）。
- **落点**｜tools/build_pack.py、pack/modrinth.index.json


## ADR-02　一开始就按“客户端 + 专用服务端”双端交付

- **问题**｜Q2　只要客户端，还是客户端 + 服务端双端？（默认：客户端优先，保证 LAN 可用）
- **决策**｜双端交付，以保证和朋友正常联机。
- **理由**｜LAN 直连和独立服务端对模组的加载路径不同，只测客户端等于没测服务端。
- **代价**｜直接引出后面最难的一个问题：4 个客户端专用模组会让专用服务端在加载 net.minecraft.client.* 时崩溃（invalid dist DEDICATED_SERVER），必须单独维护排除名单。
- **落点**｜tools/pack_plan.py 的 SERVER_EXCLUDE、tools/server_smoke.py


## ADR-03　增量全部做在附属模组里，不改第三方 jar（全项目最重要的一条）

- **问题**｜Q4★　新增玩法用什么实现？（本人答：以可以长期让 AI 或者人类开发的角度来实现，我不懂编程，但希望这个项目可以长久）
- **决策**｜新增玩法一律实现在自研附属模组 witherchallenge 中；第三方 jar 原件不动，确需改动时先复制副本、只改副本，并记录回滚方式。
- **理由**｜这是「长期可维护」这一诉求的直接落地。原 jar 一旦被改，上游更新就无法合并，接手的人也说不清哪一行是原作者的、哪一行是后加的。副本 + 回滚记录把改动变成可追溯的。
- **代价**｜只能走事件、反射、Mixin 这些扩展点，受原模组暴露的接口限制；扩展点不够时不得不写 Mixin，可读性下降。
- **落点**｜addon/（40 个 Java 源文件）、patched_mods/、CHANGELOG.md 的变更纪律


## ADR-04　继承既有材料，但“先查冲突再决定合并”

- **问题**｜Q7★　classcial_mods 的四个 jar 是否全装？凋暴包里那 57 个 mod 怎么处理？（本人答：都是材料，大部分直接搬、少部分要改；两边和本项目可能有冲突和重叠，必须检查后决定）
- **决策**｜不整体复制、也不从零重建：先做模组清单比对与冲突检查，再逐项决定「搬 / 改 / 换 / 删」。
- **理由**｜避免重复造轮子，同时防止把两套设计的重叠部分硬拼在一起产生隐性冲突。
- **代价**｜前期要多花一轮比对成本；结果是删掉 4 个（重复 modid、版本不符、无引用残留）、换掉 2 个版本、改动 1 个副本（修复其 396 份损坏的战利品表与模型）。
- **落点**｜task/mod冲突检查报告.docx、tools/pack_plan.py、tools/patch_wwst.py


## ADR-05　版本由下游硬约束决定，不追上游最新版

- **问题**｜Q8★　CWS 用哪个构建？geckolib 用哪个版本？（本人答：主要依照凋暴整合包来改；geckolib 依照 W.A.R. 的要求）
- **决策**｜CWS 跟随凋暴包的既有构建；geckolib 取 W.A.R. 文件名所要求的 4.8.4，而非更新的 4.8.2/其他版本。
- **理由**｜geckolib 是 W.A.R. 的硬依赖，版本不匹配直接崩；此处「上游最新」没有意义，能跑通的下游约束才是唯一标准。
- **代价**｜放弃部分更新特性；两个构建重复时还要处理重复 modid。
- **落点**｜classcial_mods/、tools/pack_plan.py 的版本固定


## ADR-06　主动砍掉“跨维度追踪”——用实现风险否决功能完整性

- **问题**｜Q75　「持续跟踪玩家」的规则？（默认：凋暴一直追）
- **决策**｜凋暴锁定主世界，不跨维度：玩家在主世界内无论多远都持续追踪；玩家进入地狱、末地或其他模组维度后，凋暴留在主世界，玩家回主世界后继续追。跨维度传送取消。
- **理由**｜两条明确的实现代价：末地外岛／末地环的坐标换算复杂且易错；凋暴是多部件实体，跨维度传送时部件错位的风险高。与其做一个会出 bug 的功能，不如不做。
- **代价**｜牺牲了「追杀到地狱」的压迫感，玩法上留了个缺口。
- **落点**｜addon/.../world/WitherAnchorData.java、WitherPresence.java


## ADR-07　用攻速补攻击力，维持 DPS 平衡

- **问题**｜Q49★　刀的攻速 4.5 是笔误吗？（4.5 比剑的 1.6 快得多）
- **决策**｜攻速就是 4.5，不改。
- **理由**｜「攻击力低必须攻速补」——单次伤害低是设计意图，用高攻速维持总输出（DPS），手感上是「快而轻」而不是「慢而重」，与斧形成明确的武器分工。
- **代价**｜高攻速对判定帧与耐久消耗更敏感，平衡窗口更窄。
- **落点**｜addon/.../registry/ModTiers.java、Combat 相关事件


## ADR-08　数值目标可以因实现难度让步

- **问题**｜Q61　加强版 corpse 的血量也是 100 吗？（本人答：想改成 150，如果技术实现比较难就 100）
- **决策**｜目标值 150；若实现代价过高则回退到 100，并要求回报最终值。
- **理由**｜把「想要的体验」和「必须付的成本」分开谈，并给执行方留了明确的回退条件和回报义务。
- **代价**｜玩家侧看到的数值可能低于设计意图。
- **落点**｜addon/.../combat/CorpseRules.java


## ADR-09　稀有掉落用「基础概率 + 抢夺加成」建模

- **问题**｜Q19★　10% 是否受抢夺影响？哪些击杀方式算数？（本人答：抢夺每级 +5%）
- **决策**｜基础 10%，抢夺每级 +5%；并限定击杀来源（玩家或其驯服狼）。
- **理由**｜沿用原版附魔的经济语义，玩家不需要额外学习成本；限定来源可防止刷怪塔/环境伤害白嫖。
- **代价**｜需要在 LootEvent 里判定击杀来源，比单纯随机数复杂。
- **落点**｜addon/.../combat/LootEvents.java


## ADR-10　让玩家也成为感染链的一环

- **问题**｜Q34★　排除名单还有哪些？对玩家生效吗？（本人答：玩家有效，被击中会有 1 小时凋灵效果并感染凋零腐败）
- **决策**｜感染箭对玩家同样生效：命中后获得 1 小时凋灵效果，并附加「凋零腐败」。
- **理由**｜如果只有怪物会被感染，玩家就没有「误伤自己」的风险，感染机制会退化成单向增益。对玩家生效把风险对称化，玩法张力回来了。
- **代价**｜多人环境下可能误伤队友，需要配置项来调和（见 ADR-11）。
- **落点**｜addon/.../combat/SicknessControl.java、UndeadConversion.java


## ADR-11　影响强度的参数一律外置到配置

- **问题**｜Q37／Q52／Q81　宠物是否被感染？斧的 PvP 伤害？锁血期能否被 /kill？（本人答：都通过配置改；默认宠物有效、默认完全免伤）
- **决策**｜凡是会改变强度或公平性的参数，都做成 config 项，而不是写死在代码里。
- **理由**｜同一个整合包要同时服务单人挑战和多人联机，两边的合理数值不同，把差异留给配置比维护两个版本划算。
- **代价**｜配置项增多，需要有默认值和说明，否则玩家不知道能改什么。
- **落点**｜addon/.../WCConfig.java


## ADR-12　主动放弃做纪念品——范围管理的“不做”

- **问题**｜Q99　通关奖励和成就？（本人答：默认，但没有纪念品——不想设计贴图，而且认为执行方的贴图设计能力不行）
- **决策**｜成就体系照做，通关纪念品不做。
- **理由**｜贴图是短板，与其交付一个拉低整体质感的物品，不如不做。对一个以「氛围与压迫感」为卖点的挑战包，劣质美术是负资产。
- **代价**｜通关少了一个可炫耀的实物奖励，成就感只能靠成就系统承载。
- **落点**｜addon/.../registry/ModCriteria.java、9 个 advancements JSON


## ADR-13　引导用原版「书与笔」，零开发成本

- **问题**｜Q96　挑战怎么开始？要不要给一本指南书？（本人答：用原版物品书与笔写好，放物品栏第一格，UTF-8，中文，作者署名）
- **决策**｜不做自定义 GUI 或引导流程，直接把挑战指南写成原版成书，进世界即在物品栏首位。
- **理由**｜自定义 GUI 要写 Screen、要处理本地化、要兼容分辨率，成本高；原版书与笔是现成载体，玩家开局第一眼就能看到，阅读体验也符合「古卷」的调性。
- **代价**｜排版能力受限（分页、无图），长文本阅读体验一般。
- **落点**｜addon/.../item/GuideBook.java、GuideBookEvents.java
